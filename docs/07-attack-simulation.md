# Task 7: Attack Simulation

All attacks were run against the throw-away repository `sonujha78/novapay-supply-chain` and the local `kind` cluster `novapay-lab`. Evidence files are under `evidence/task7/`.

## Attack Log

| # | Attack | Expected result | Actual result | Detection vs Prevention |
|---|--------|------------------|----------------|--------------------------|
| A1 | Deploy an image pushed from a laptop (not signed by CI) to the trusted registry path | Admission controller rejects the pod | **Rejected.** Kyverno: `.attestors[0].entries[0].keyless: no signatures found` (reused the Task 2 pre-signing tag as the unsigned stand-in). See `evidence/task7/A1-unsigned-laptop-image.txt`. | **Prevention** — blocked before the pod is ever admitted. |
| A2 | Sign an image with the same repo's workflow but from an untrusted ref (fork-equivalent) and deploy it | Rejected: certificate identity does not match the policy | **Rejected.** Kyverno: `subject mismatch: expected .../build-sign-attest.yml@refs/heads/main, received .../build-sign-attest.yml@refs/heads/attack-a2-untrusted-ref`. See `evidence/task7/A2-wrong-identity.txt`. | **Prevention** — a real signature exists, but the identity check still blocks it. |
| A3 | Overwrite an image tag with different content; deploy by tag | Detected: signature/digest mismatch. Explain why deploying by digest matters | Every Pod manifest and the Kyverno policy in this repo reference `image@sha256:<digest>`, never a mutable tag. An overwritten tag therefore has zero effect on what is actually deployed — there is nothing for a tag-overwrite attack to redirect. See `evidence/task7/A3-tag-overwrite-digest-matters.txt`. | **Prevention by design** — digest pinning removes the attack surface rather than detecting it after the fact. |
| A4 | Open a PR (or, as admin, push directly) that edits the workflow to print secrets or add `id-token: write` to an unrelated job | Blocked or neutralised by permissions, branch protection, and required reviews | **Partially blocked.** The repository ruleset flags the push as violating "PR required" and "signed commits required", but the repo admin has a bypass (`bypass_mode: always`), so the push still succeeded for the admin account. A non-admin contributor would be hard-blocked. `permissions: {}` at the workflow root plus per-job least privilege (`id-token: write` only on `sign`) limits the blast radius even if a malicious job were merged. See `evidence/task7/A4-workflow-edit-blocked.txt`. | **Detection + partial prevention** — full prevention requires removing the admin bypass, which is impractical for a solo lab and is logged as a known gap (Task 8). |
| A5 | Simulate a compromised build step that modifies the artifact after the build | Discuss how the separate provenance job and digest verification expose the change | Digest pinning means any tampered artifact has a different digest than a known-good one, exposing drift on comparison. However, SLSA provenance at the achieved **L2** level does not prove the `build` job's internal steps were untampered — only L3 (isolated provenance generation, e.g. `slsa-github-generator`) closes this gap. See `evidence/task7/A5-A6-discussion.md`. | **Detection only, and only after comparison** — this is an acknowledged gap at the current SLSA level. |
| A6 | A dependency in the lockfile is replaced by a vulnerable or malicious version | Vulnerability gate or dependency review flags it; SBOM shows exactly where it entered | `go.sum` hash pinning rejects a naive local swap at build time. A genuine compromised upstream release would not be caught before merge, but the SBOM (Task 3) records exact component versions for every build, letting an incident response instantly identify every affected artifact once a compromise is disclosed. The grype gate only catches versions with a known, fixed CVE — not zero-days or planted backdoors. See `evidence/task7/A5-A6-discussion.md`. | **Detection (post-disclosure), not prevention** — a targeted, novel malicious dependency is not blocked before merge. |

## Attacks this setup does not fully stop

- **A4:** the repository admin's ruleset bypass means a compromised or malicious admin account can still push directly to `main`, bypassing PR review and signed-commit requirements. Acceptable for a solo lab; not acceptable for production without removing the bypass or requiring a second approver even for admins.
- **A5:** tampering inside the `build` job itself, before the image is pushed, is not detected by this pipeline in real time — only exposed after the fact by digest comparison against a previously-trusted build. Reaching SLSA Build L3 is the documented next step.
- **A6:** a novel, targeted malicious dependency with no published CVE is not blocked pre-merge by any automated gate in this pipeline; it relies on PR review and `go.sum` integrity alone.
